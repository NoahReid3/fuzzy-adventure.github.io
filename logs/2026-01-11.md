### Understanding fuzzy string matching

Learned how the app implements fuzzy matching to handle typos and variations in user input. The app uses the **Levenshtein distance algorithm** to calculate how similar two strings are.

**Levenshtein distance** calculates the minimum number of single-character edits (insertions, deletions, or substitutions) needed to transform one string into another. For example:
- "hello" and "hello" have a distance of 0 (identical)
- "cat" and "bat" have a distance of 1 (one substitution)
- "kitten" and "sitting" have a distance of 3 (multiple edits)

The app then converts this distance into a **similarity score** between 0 and 1:
- 1.0 = identical strings
- 0.85 = 85% similar (the threshold used)
- 0.0 = completely different

This allows the quiz to accept answers like "3000 people displaced" even if the user types "3000 new people displaced" with a typo, as long as the similarity is above 85%.

### Understanding TypeScript concepts

While examining the code, learned several important TypeScript concepts:

**Constants (`const`):**
- `const` means the value cannot be reassigned after it's created
- It's a constant value, not a variable

**TypeScript generics:**
- TypeScript supports **generics**, which allow functions to work with any type
- Syntax: `<T>` where `T` is a type parameter
- Example: `function shuffleArray<T>(array: T[]): T[]` can work with arrays of any type
- This makes code reusable without needing separate functions for each type

**Arrow functions:**
- Arrow functions are a shorthand way to define functions in TypeScript/JavaScript
- Syntax: `const functionName = (args) => { ... }`
- Equivalent to using the `function` keyword, but more concise
- Example: `const shuffleArray = <T>(array: T[]): T[] => { ... }`

**Type manipulation (`Omit`):**
- `Omit<T, K>` is a TypeScript utility type
- It constructs a new type with properties from `T`, except those in `K`
- Example: `Omit<IonChargeQuestion, 'options'>` creates a type without the `options` property
- This is advanced TypeScript that allows flexible type definitions

**The spread operator (`...`):**
- The `...` operator copies elements from one array into another
- Example: `const shuffled = [...array]` creates a copy of the array
- Used to avoid mutating the original array

**For loops and array iteration:**
- Learned about iterating backwards through arrays: `for (let i = array.length - 1; i > 0; i--)`
- Convention: `i` is the first index variable, `j` is the second, `k` is the third (alphabetical order)
- This is used in the shuffle algorithm to randomize array order

### Understanding the shuffle algorithm

Examined the shuffle algorithm used to randomize quiz questions:

```typescript
const shuffleArray = <T>(array: T[]): T[] => {
  const shuffled = [...array];
  for (let i = shuffled.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [shuffled[i], shuffled[j]] = [shuffled[j], shuffled[i]];
  }
  return shuffled;
};
```

How it works:
1. Creates a copy of the original array
2. Iterates backwards through the array
3. For each position, picks a random position earlier in the array
4. Swaps the current element with the randomly chosen element
5. Returns the shuffled array

This ensures questions appear in a completely random order each time.

### Understanding unit tests

After refactoring, learned about **unit tests** – automated tests that verify code works correctly.

**What are unit tests?**
- Small pieces of code that test individual functions or components
- They run automatically and check that code behaves as expected
- If you make a change that breaks something, tests will fail and alert you

**Why unit tests are important:**
- **Catch bugs early:** Find problems before they reach production
- **Prevent regressions:** Ensure changes don't break existing functionality
- **Documentation:** Tests show how code is supposed to work
- **Confidence:** You can refactor or change code knowing tests will catch mistakes

**In professional environments:**
- Teams have thousands of unit tests
- Tests run automatically on every commit (on a CI/CD server)
- You can't merge code until all tests pass
- This ensures the main branch always has working code

**Example test structure:**
```typescript
describe('Levenshtein distance', () => {
  it('returns 0 for identical strings', () => {
    expect(levenshteinDistance('hello', 'hello')).toBe(0);
  });
  
  it('returns correct distance for single character differences', () => {
    expect(levenshteinDistance('cat', 'bat')).toBe(1);
  });
});
```

- `describe()` groups related tests together
- `it()` defines a single test case
- `expect()` checks that a value matches what's expected
