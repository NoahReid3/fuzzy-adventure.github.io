### NPM vs pnpm

For TypeScript and JavaScript projects, there are several package managers available:

- **NPM (Node Package Manager)** – The original and default package manager for the JavaScript runtime environment (Node.js). It's the largest single language code repository in the world. Commands include:
  - `npm install <package-name>` – installs a package into the local directory
  - `npm publish` – publishes your own package to the repository

However, NPM has drawbacks: it's slow, insecure, and not very efficient.

- **pnpm** – A better alternative that we're going to use. It's faster, more secure, and more efficient than NPM. It makes development life easier.

### Project scaffolding

Learned the term **scaffolding**, which is a common term in software engineering. Scaffolding means setting up an empty project so that it's ready to start developing. It takes an empty project and configures everything needed to begin work – it doesn't add any particular functionality, just gets everything ready.

This is similar to what happened when asking how to install Tkinter into Python – that was a form of scaffolding a Python project, but we're going to go much further with the web application.

### Using Cursor's Plan mode

Before scaffolding the React/TypeScript application, learned about **Plan mode** in Cursor, which is different from Agent mode or Ask mode:

- **Ask mode** and **Agent mode** are "one-shot" prompts – you just let it rip (YOLO – You Only Live Once), and it makes changes. Because everything is in Git, if anything goes wrong, you can just revert all the changes.

- **Plan mode** is different and quite useful:
  - It creates a detailed plan before making any changes
  - Lets you, the human operator, review the plan first
  - Often asks clarifying questions (e.g., "Should the React application be in the root directory or a subdirectory?")
  - Shows a list of todos/steps it will execute
  - Allows you to edit the plan or request changes before execution
  - Gives you an opportunity to review what it's going to do before it does it
  - After execution, you can review what it actually did

The workflow: Review the plan → approve or modify → execute → review results.

This is valuable because you can scan the plan and decide "that looks about right" or "that's completely wrong" before any code changes are made.

### Installing project dependencies

After scaffolding, the packages are listed in `package.json`, but they haven't been downloaded yet. To install them:

```bash
cd web
pnpm install
```

This command:
- Reads `package.json`
- Figures out all the dependencies (and their dependencies, and so on)
- Downloads all the required packages
- Stores them in a `node_modules/` folder

The process can download "trillions" of packages (actually thousands, but it feels like a lot) because each package has its own dependencies, which have their own dependencies, creating a dependency tree.

### Building the project

After installing dependencies, built the project:


This command:
- Transpiles TypeScript into JavaScript (as discussed in previous sessions)
- Bundles all the code together
- Optimizes it for production
- Creates a `dist/` folder with the built JavaScript files

Even for a simple "Hello World" app, there's quite a lot going on in the build process. This is normal – modern web development involves many tools working together.

### Understanding .gitignore

After building, Git was trying to track thousands of files (showing "10,000 changes"). This is because:

- `node_modules/` contains all the installed packages
- `dist/` contains the built output files

**We don't want to commit these to Git** because:
- They're not source code – they're installed packages and build outputs
- They can be regenerated on any machine by running `pnpm install` and `pnpm build`
- They make the repository huge and slow
- Different developers might have slightly different versions

**Solution:** Create a `.gitignore` file that tells Git to ignore these folders.

Asked Cursor to create a `.gitignore` file for TypeScript/React projects. It automatically includes patterns to ignore:
- `node_modules/` – installed packages
- `dist/` – build output
- Other common files that shouldn't be tracked (like `.env` files, IDE settings, etc.)

After adding `.gitignore`, Git went from tracking 10,000+ files down to just 18 files (the actual source code and configuration files). The ignored files are greyed out in Cursor's file explorer.
